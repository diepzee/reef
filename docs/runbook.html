The gating check GO / NO-GO

Her assistant living in the Claude mobile app rests on two unproven assumptions: that a custom MCP connector works on her plan tier, on mobile, and that Claude's connector OAuth (which demands Dynamic Client Registration) completes against WorkOS AuthKit. The spike burns both down with zero real data at stake.

  1. Create a free WorkOS account → application with AuthKit enabled. Note the *.authkit.app domain.
  2. Dashboard: enable Dynamic Client Registration. Check the Redirects tab — the spike flagged (unverified) that a callback entry may or may not be needed; record what you find.
  3. Deploy the spike:

railway up   # again, so the vars take
  4. claude.ai web, your account: add https://<domain>/mcp as a custom connector → AuthKit login appears → sign in → call whoami.

Who is allowed in

WorkOS authenticates anyone who signs up. The invite tool is what turns authenticated into allowed — no migration edit, no signup form. Inviting an email creates that person's row and their membership row before they have ever signed in; anyone nobody invited is denied by principal_from_claims.

  1. As the space's owner, from any connected assistant: 
    invite(space="school", email="<her-email>",
       display_name="<her-name>")
    Say out loud what it grants first: permanent access to everything in that space, past and future.
  2. She signs in to AuthKit with that exact address, verified. Her personal space and its two starter pages appear on that first sign-in. The email must match exactly — it is what her first login binds to.

    she calls list_spaces and sees her own personal space plus school.

4

Storage & safety nets

R2 holds image bytes; Postgres holds everything else. GitHub used to give durability for free — now it's yours to arrange, in three layers: managed backups (belt), your own dumps to R2 (braces), bucket versioning (the undo button for bytes that aren't in any dump).

  1. Cloudflare → R2 → create bucket rif, enable object versioning. Create an S3 API token, then: 
    railway variables \
  --set RIF_S3_ENDPOINT=https://<account-id>.r2.cloudflarestorage.com \
  --set RIF_S3_BUCKET=rif \
  --set RIF_S3_ACCESS_KEY=<key> --set RIF_S3_SECRET_KEY=<secret>
railway up
  2. Create/confirm a BYPASSRLS role on Railway's Postgres and give scripts/backup.py that connection string — distinct from the app's DATABASE_URL. (See the trap.)
  3. Enable Railway's managed Postgres backups in the dashboard.
  4. Schedule scripts/backup.py as a daily Railway cron — it streams pg_dump straight to R2, never to container disk (which is ephemeral).
  5. The drill: one real backup → download from R2 → restore into local scratch per docs/restore.md → check: 
    select (select count(*) from pages)       pages,
       (select count(*) from revisions)   revisions,
       (select count(*) from memberships) memberships;

    counts match production. If memberships is 0, the backup is decorative.

The pg_dump trap

The RLS design works too well: FORCE ROW LEVEL SECURITY means even the table owner sees zero content rows without a principal set — and pg_dump connects with no principal. A backup run as the app role fails. Reproduced locally, not theorized. The backup connection must carry BYPASSRLS.

Protocol & personas

The code ships a fallback protocol, but the real thing is content, editable like any page and versioned like any page.

  1. Write meta/protocol.md in your personal space (via update_meta_page, or just ask a connected assistant): load context first · compile, don't dump · private-by-default routing · promote only with consent — plus the onboarding behavior: an assistant meeting an empty personal space introduces itself, asks what to call itself, and interviews gently to seed the persona. The protocol and the persona are per-person: update_meta_page refuses any space but personal, and get_operating_protocol never reads a shared space's copy.
  2. Write your own meta/persona.md, also in your personal space — Mark's tone lives in mark/wiki/mark.md today; port it.
  3. Hers is not yours to write. Anyone invited gets both pages seeded in their own personal space at first sign-in; her first conversation fills the persona in. She names her own assistant.
7

Measure the ceiling

The server budgets body characters; the client cares about serialized tokens, and the mobile host may truncate big tool results on its own. The budget must come from measurement on the real device, not arithmetic.

  1. railway run uv run python scripts/measure_context.py wouter@rugvin.be <size> — pad the corpus to ~60 KB, then ~200 KB, then ~500 KB.
  2. After each: from the Claude mobile app, ask the assistant to load_all_context and report page_count, included_count, and whether every non-null body arrived intact — a mismatch means truncation in transit, by design detectable.
  3. Record in docs/superpowers/plans/context-limits.md; set RIF_CONTEXT_CHAR_BUDGET comfortably below the first size that misbehaved; railway up.
  4. Clean up: scripts/measure_context.py wouter@rugvin.be 0.
