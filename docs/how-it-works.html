How it works

One memory service, two assistants, three spaces. This explains the machine you're about to deploy: where knowledge lives, how the privacy boundary is enforced, what happens during a conversation, and why the design refuses some fashionable ideas on purpose.

The big picture

rif is a small headless Python service. It owns a Postgres database (the knowledge), talks to R2 (image bytes), and exposes everything as MCP tools over HTTPS. Every surface — her Claude app, your Claude Code, anything later — is just another client of the same tools. One store, one write path, one enforcement point.

Three spaces, and who may enter

Knowledge lives in spaces: one personal space each, one shared household space. Access is a table of memberships — and the whole privacy model is the absence of two rows.

What happens in a conversation

  1. Login, once. The Claude app discovers WorkOS through rif's metadata and runs the OAuth flow. WorkOS says who she is; the two-row persons table decides whether she's allowed. An authenticated stranger is denied.
  2. Load everything. The assistant's first call is load_all_context — every page in every space she can see, in one response. No search, no retrieval ranking, no "the model didn't find the page." At this scale (~100 pages fits comfortably) complete memory is simply affordable.
  3. Talk. The model reasons over full knowledge in context. Image descriptions ride along as text; pixels are fetched only when they matter.
  4. Remember. New facts land via remember(fact) — which defaults to the private space in its very signature. Only clearly-household facts (joint things, joint decisions, shared obligations) go to household, and anything ambiguous stays private.
  5. Compile. Real edits go through edit_page_section — surgical, versioned, conflict-checked. Every write records who, why, and the full page state, forever.

If the corpus ever outgrows the context budget, the payload says so out loud: omitted pages still appear, body-less, with a note — a partial memory that looks complete is the one failure this design refuses to permit.

The boundary: the database refuses

The rule "her sessions can't read your health pages" is not enforced by application code being correct. It's enforced by Postgres Row-Level Security in FORCE mode: every content-table query is filtered by policies that join through memberships, and they bind everyone — including rif's own database role.

Why this matters The first draft enforced the boundary by discipline — "every query must remember the filter." External review showed the plan itself already broke that rule. Discipline doesn't survive contact with future code; a database that refuses does.

Sharing is a one-way door

Promoting a page from personal to household is the one irreversible act in the system: once the other person could have read it, there is no un-sharing. So there is no demotion tool at all, and promotion takes two steps — because a model passing confirm=true on its own proves nothing.

Sharing can be smaller than a page — but never a fragment. To share one section, the same flow extracts it: the section becomes its own page in the household space, and the source keeps a marker where it was. The disclosure the user approves is exactly the text that moves; the rest of the page — and its entire history — never leaves the personal space. Extraction also forces the shared text to stand alone, so what the reader sees is what the owner approved, with no private context bleeding along.

Memory of the memory

Every write stores a complete snapshot — body, title, tags — plus who wrote it, when, and a one-line why. That's git's model, kept in a table, which makes it queryable: "what did we know about the boiler in March" is a WHERE clause, not an archaeology dig. Restoring an old version is just writing it again — history only ever grows.

Each space also carries a version counter bumped by every write, so a client can ask "did anything change?" for free — and a future changes_since tool can open her conversations with "since yesterday, Wouter noted the boiler service is booked."

Images: descriptions in memory, pixels on demand

Bytes go to R2; Postgres keeps the metadata plus a mandatory text description, written at upload time. That description is what makes photos work in a load-everything design: "the boiler's model plate, reading Vaillant ecoTEC VU 246/5-5" rides along in every context load, and the actual image is fetched — via a short-lived signed URL, behind the same space check as any page — only when the pixels matter.

Safety nets

  1. Railway managed backups — the belt.
  2. Daily pg_dump streamed to R2 — the braces, run by a role that may bypass RLS (the boundary works so well it blanks backups run as the app).
  3. R2 object versioning — the undo button for image bytes, which no database dump contains.
  4. The export — python -m rif.export renders every space back to plain markdown with frontmatter, import-compatible. If rif dies, is abandoned, or you simply change your mind, the knowledge walks away as files. The store is never a hostage.

What it deliberately doesn't do

AbsentWhy
Full-text searchThe whole corpus loads — there is nothing to search.
Vector DB / embeddingsRetrieval tech for corpora that don't fit in context. Top-k similarity fails silently — the assistant confidently not knowing what it was told — the worst failure a memory can have.
Knowledge graphSame reason; and the wiki already is one — pages are nodes, links are edges — with the nuance kept in prose instead of lossy triples.
Demotion / unsharingCan't exist honestly. Once readable, read. The only gate is before sharing, which is why that gate is heavy.
Notion / bidirectional syncTwo writable copies of the truth means a conflict-resolution problem that never ends. The export is one-way on purpose.
A web UIBoth users talk to assistants; the assistants talk to rif. A UI for nobody is the feature most worth not building.
