How it works

rif is one memory service for two assistants — yours and hers. This page explains four things: where knowledge lives, who can see what, what happens during a conversation, and why some popular features were left out on purpose.

The big picture

rif is a small Python service with no user interface. It stores pages in a Postgres database. It stores image files in R2. It offers its tools over HTTPS using MCP — the protocol Claude uses to call external tools.

Every surface is a client of the same tools: her Claude app, your Claude Code, and anything added later. There is one store, one write path, and one place where access is enforced.

Your cove, and the coves you share

Knowledge lives in coves. Every person gets exactly one personal cove, created automatically the first time they sign in. Beyond that, a cove is a named group of people — a household, a school run, a small project — started by whoever needs it and addressed by a short slug, like school.

A membership table records who may enter which cove. Every reader's access is one row in that table: their name, and the cove. The privacy model is simple to state, and the database — not the application code — enforces it: a cove's pages are readable by exactly its members, and by no one else.

Joining a cove

The owner of a shared cove invites people in by email — there is no other door. Inviting an unknown address creates that person's record on the spot, plus a membership row joining them to the cove, before they have ever signed in.

The first time someone signs in with that exact, verified email, rif recognizes the standing invite and finishes onboarding in the same transaction: their own personal cove appears, with two starter pages waiting — a protocol page and a persona page for them to fill in. There are no invite links to click and no open signup form. An email nobody invited is denied, exactly as before.

What happens in a conversation

  1. Log in once. The Claude app finds WorkOS through rif's metadata and runs the login flow. WorkOS answers who she is. The two-row persons table decides whether she is allowed in. A stranger with a valid login is still denied.
  2. Load the index. The assistant's first call is load_index. It returns the map: every page she can see, with its title, tags, and a one-line description, plus image descriptions. No page bodies. The description comes from the page's own opening summary, so the map is curated, not clipped at random.
  3. Fetch what matters. The assistant reads the map, picks the entries this conversation needs, and fetches them with read_pages. When a new topic comes up, it fetches again. The rule in the protocol: never answer from the index's descriptions alone.
  4. Remember. New facts go through remember(fact). Its default target is the private cove — the default is in the function signature, not in a guideline. Only clearly shared facts (joint things, joint decisions, shared duties) go to a shared cove. Anything unclear stays private.
  5. Compile. Lasting edits go through edit_page_section: small, precise changes with a version check. Every write records who wrote it, why, and the full page state. That record is permanent.

This is the original wiki discipline — read the index, open only what you need — run by the service instead of by convention. A bulk tool (load_all_context) still exists for maintenance jobs that genuinely need every page at once; when its result is cut short, it says so rather than looking complete.

The privacy boundary

The rule: her sessions can never read your private pages, and yours can never read hers.

Application code does not enforce this rule. The database does. Postgres row-level security (RLS) filters every query on the content tables: it returns only rows that belong to a cove the current person is a member of. The policies run in FORCE mode, which means they also bind rif's own database account.

Why this matters The first design enforced the boundary with a coding rule: "every query must remember the filter." An external review showed the plan itself already broke that rule. Rules of discipline fail when future code forgets them. A database that refuses does not forget.

Sharing cannot be undone

Sharing moves content from your personal cove to a shared cove you belong to. Once its members could have read it, taking it back means nothing. So there is no unshare tool, and sharing takes two steps. One step would not be enough: a model can pass confirm=true on its own, and that proves nothing about what you agreed to.

You can share one section instead of a whole page. The service extracts the section: it becomes its own small page in the destination cove, and the source page keeps a marker where it was. What you approve is exactly the text that moves. The rest of the page — and its full edit history — stays private. Extraction also forces the shared text to stand alone, so no private context around it travels along. The disclosure names every current member of the destination cove, so you confirm who will see it, not only where it goes.

History

Every write stores a complete snapshot: body, title, and tags, plus who wrote it, when, and a one-line reason. This is git's model, kept in a database table. A table can be queried: "what did we know about the boiler in March?" is one WHERE clause. To restore an old version, the assistant writes it again. History only grows.

Each cove also has a version counter. Every write increases it. A client can ask "did anything change?" at almost no cost. A future changes_since tool can use it to open her conversations with: "Since yesterday, Wouter noted the boiler service is booked."

Images

Image files go to R2. Postgres keeps the details, plus a required text description written when the image is stored. The description travels with every context load — for example: "the boiler's model plate, reading Vaillant ecoTEC VU 246/5-5." The image itself is fetched only when the pixels matter, through a link that expires after five minutes and is issued only after the same cove check as any page.

Safety nets

  1. Railway's managed backups — automatic database backups by the hosting provider.
  2. A daily dump to R2 — rif's own backup, stored with a different provider than the database. It runs under a database role that may bypass RLS, because the boundary works so well that a normal backup run reads nothing.
  3. R2 object versioning — old versions of image files survive deletion. No database dump contains the files, so this is their only net.
  4. The export — python -m rif.export writes every cove back to plain markdown files. The format matches the importer, so a lost database can be rebuilt from it. If rif dies or you change your mind, the knowledge leaves as files. The store never holds it hostage.

What it leaves out, on purpose

Left outWhy
Full-text searchThe index is small enough to read whole, and its descriptions are the retrieval surface. The model retrieves by reading the map, not by querying an engine.
Vector databaseA retrieval tool for corpora far too big for an index. Its failure is silent: the assistant does not know something it was told, and does not know that it does not know. An index the model reads in full fails visibly instead.
Knowledge graphSame reason. The wiki already is a graph — pages are nodes, links are edges — and it keeps nuance in prose instead of losing it in extracted facts.
UnsharingCannot exist honestly. Once readable, read. The only real gate is before sharing. That is why that gate is heavy.
Notion, or any two-way syncTwo writable copies of the truth create conflicts forever. The export is one-way on purpose.
A web interfaceBoth of you talk to assistants. The assistants talk to rif. An interface with no users is the feature most worth not building.

The tools, at a glance

ToolWhat it does
load_indexThe map: every page's title, tags, and one-line description. The first call of every conversation.
read_pages / read_pageFetch the entries the conversation needs, chosen from the index.
load_all_contextEvery page body at once. Maintenance only.
rememberAdds a fact to the inbox. Private by default. Safe to retry.
write_page / edit_page_sectionFull or precise edits, with a version check against lost updates.
prepare_to_share → confirm_shareTwo-step sharing — a whole page, or one extracted section (section + dest_path).
update_meta_pageThe only way to change the protocol and persona pages — the pages that steer the assistant.
add_image / read_imageStore an image with a required description. Fetch it through a short-lived link.
delete_imageThe one thing here that really deletes: an image and its description, for a bad upload or a photo added to the wrong cove. Confirm with the person first — the bytes do not come back.
get_operating_protocolLoads the protocol and persona. They are pages, versioned like all pages.
list_covesWhat you can see: your personal cove and every shared cove you belong to — with each cove's member list, because knowing who is in the room is what informed sharing means.
create_coveStart a new shared cove with a slug. You become its owner.
invite / remove_memberOwner-only. Add or remove a member by email. Removing stops future access; it cannot unshare what was already read.
